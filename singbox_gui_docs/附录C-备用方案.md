# 附录C 备用方案

正文采用“官方未修改守护进程 + 项目自签名证书”的方案。本附录为历史方案，不属于当前开发范围。A-29 中的失败条件只触发阻塞报告，不构成实施授权；仅产品负责人明确改变“官方后端不改”的目标后才可重新评估。启用任一方案前，须先更新 2.3、2.9、15.2、17.2、21、22 章与附录 A，并重新排期。

## C.1 需要报告的阻塞（不自动授权启用）
- M0 实机签名验证（20.5 SIG-01～SIG-08）在任一目标系统上失败，且无法通过调整证书规格（21.1.2）解决；
- 作者不同意 17.2.1 所列不可更改的技术标识（`sing-box.exe`、服务名 `sing-box-daemon` 等），且不愿以非公开方式发布；
- 上游守护进程删除或收紧对自签名签名者的接受（22.2 接口差异检查会以议题提示）。

## C.2 方案一：维护守护进程分支（历史备选）
做法：在本项目仓库中以补丁形式维护对 `experimental/boxdd` 的少量修改，其余与正文相同（仍由 `build_boxdd` 从上游标签构建，GUI、worker 协议、安装器与更新流程不变）。

| 修改点 | 内容 |
|---|---|
| 签名者判定 | 把“GUI、worker 与守护进程签名证书逐字节相同”改为“签名证书等于编译时固定的项目证书”（固定证书指纹）；或在源码构建中允许未签名，但仅当文件位于受保护安装目录且与守护进程同一安装布局时 |
| 自签名有效期 | 可选：对固定证书不再检查 `NotAfter`，消除证书过期导致的整体不可用（21.1.3） |
| 名称与路径常量 | 若名称同意被拒：服务名、管道名、GUI 文件名、注册表键、默认数据目录改为本项目名称（集中在 boxdd 的常量文件） |
| `InstallUpdate` 产品名 | 改为本项目安装包的 `ProductName`，使无 UAC 更新可用（A-26） |

- 补丁存放：`patches/boxdd/*.patch`，由 `scripts/daemon/build.ps1` 在构建前应用；补丁应用失败视为接口变化，按 22.2 开议题，不自动发布。
- 维护成本：每次上游发布需人工确认补丁语义仍正确（约 0.5 天/次）；大版本重构时可能需重写补丁（约 2～3 天）；因修改了守护进程，产物不再是“官方未修改守护进程”，About 与 README 须注明“随附修改版守护进程”，并按 GPLv3 提供补丁源码。
- 工期影响：约 +1 周（补丁、构建脚本、CI 补丁检查、测试）。

## C.3 方案二：自有核心服务（旧设计摘要）
仅当方案一也不可行时采用。做法：不使用 boxdd，由本项目以 sing-box 的 Go 库自行实现 Windows 服务与 GUI 认证。

- 进程：`sing-box-core.exe` 以 LocalSystem 服务运行，内嵌 sing-box 核心（libbox 同等能力），暴露 StartedService/ManagedService 及自有的 HostService（版本、所有权、工作目录、报告）。
- 认证：服务管道 DACL 允许已验证用户连接；服务以管道客户端令牌识别 Windows 用户，只接受 `authorized.json` 中已授权的用户 SID；首次使用由管理员经 UAC 执行“授权此用户”；每个用户另有一把随机密钥，存于该用户 DPAPI 保护的文件中，作为调用元数据，防止同一用户下其他会话误连。
- 不依赖代码签名，因此可完全不签名发布；可额外提供不装服务的提权模式与便携版。
- 代价：需自行移植并长期维护服务、TUN、系统代理、所有权、报告与更新安装等平台代码，随上游同步的工作量显著增加；与官方桌面客户端行为不再逐项一致。
- 工期影响：约 +5～6 周，且每次上游大版本需额外 1～3 天移植。
