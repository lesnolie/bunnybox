## 2.2 选择原生 UI 而非 Web 前端的理由

MyGo 同时支持 Web 前端与原生 UI。本应用采用原生 UI，理由如下：

1. **外观保真度**：基线在 macOS 26 上使用 Liquid Glass（`glassEffect`）作为卡片与选择器材质，滚动内容在工具栏下方渐隐。MyGo 的 glass 插件只服务原生 UI，以着色器在 GPU/CPU 上绘制，提供折射、磨砂与高光边缘效果，便于按 macOS 基线调整；是否达到本应用的视觉要求须通过样板截图验证，不将框架能力直接视作验收结论。
2. **尺寸体系一致**：原生 UI 以 DIP 为单位布局，可把 SwiftUI 的 point 数值作为初始布局值；字体度量、默认控件内边距和显示缩放仍须依据基线截图校准，不能仅复制数值就认定一致。
3. **组件覆盖**：基线所需的侧边栏、工具栏、表单、分段控件、开关、列表重排、弹出菜单、代码编辑器、终端、图表绘制（`Painter`）均有原生实现；尤其 Tailscale SSH 终端在 macOS 上基于 Ghostty，MyGo 终端插件同样基于 libghostty-vt，行为与配置项可对齐。
4. **常驻资源占用**：本应用常驻托盘，原生 UI 无需 WebView2 运行时与 JS 堆，有利于控制常驻开销；实际内存与启动时间按 20.3 测量。外部网页登录认证所需 WebView2 不属于主界面。
5. **单一语言**：全部逻辑与界面均为 Go，便于 AI 代理在一个代码库中实现与测试（MyGo 原生 UI 提供无窗口测试）。

## 2.3 进程模型

本应用的进程结构、安装布局与通信方式与 sing-box-for-desktop 的 Windows 版完全一致；唯一差别是 GUI 由 MyGo 原生程序替代 Electron 程序。

| 进程 | 可执行文件与参数 | 身份 / 会话 | 作用 |
|---|---|---|---|
| GUI（application） | `<安装目录>\sing-box.exe` | 当前用户，交互会话 | 界面、托盘、深链接、配置管理、更新检查；启动并独占使用 worker |
| worker | `<安装目录>\resources\daemon\sing-box-daemon.exe worker --socket <P1> --parent-pid <GUI PID> --daemon-relay-socket <P2>` | 当前用户（GUI 子进程） | 在 P1 上提供 ApplicationService；在 P2 上把 GUI 的连接经认证后中继到守护进程管道 |
| 守护进程（daemon） | `<安装目录>\resources\daemon\sing-box-daemon.exe run --working-directory <守护进程数据目录>`（由服务控制管理器启动） | LocalSystem，会话 0，Windows 服务 `sing-box-daemon` | 运行 sing-box 核心（TUN、系统代理、路由、DNS），提供 DesktopService / StartedService / ManagedService |

```
┌──────────────────────────── 用户会话（普通权限）────────────────────────────┐
│  sing-box.exe（GUI，MyGo 原生 UI，单实例）                                    │
│    ├─ 窗口 / 托盘 / 深链接 / 文件关联 / 开机启动 / 更新检查                    │
│    ├─ SQLite：<应用数据目录>\settings.db、configs\*.json                        │
│    └─ 子进程 worker：sing-box-daemon.exe worker …                               │
│          ├─ P1 \\.\pipe\sing-box-worker.<UUID>  → ApplicationService           │
│          └─ P2 \\.\pipe\sing-box-worker.<UUID>  → 中继到守护进程               │
└──────────────────────────────────────────────────────────────────────────────┘
          │  \\.\pipe\ProtectedPrefix\Administrators\sing-box
          │  （守护进程对每个连接校验 worker 与 GUI 的路径、文件身份、签名证书，2.9）
          ▼
┌──────────────── Windows 服务 sing-box-daemon（LocalSystem，自动启动）──────────┐
│  sing-box-daemon.exe run --working-directory C:\ProgramData\sing-box-daemon     │
│    ├─ DesktopService：守护进程信息、所有权、启动服务、工作目录、报告、更新安装、 │
│    │                  非网络特权模式、语言                                            │
│    ├─ StartedService：状态/日志/分组/连接/Clash 模式/URL 测试/工具类 RPC         │
│    ├─ ManagedService：停止、重载、系统代理、调试                                 │
│    └─ sing-box 核心实例（wintun TUN、系统代理、路由、DNS）                       │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 2.3.1 worker 启动与连接（必须按此实现）
1. GUI 生成两个互不相同的管道名 `\\.\pipe\sing-box-worker.<UUID>`（UUID 为随机 v4，小写带连字符）：P1 用于 ApplicationService，P2 用于守护进程中继。
2. GUI **主进程自身**以隐藏窗口方式启动 worker，命令行必须恰好为 8 个参数，顺序固定：`sing-box-daemon.exe worker --socket <P1> --parent-pid <GUI PID> --daemon-relay-socket <P2>`（守护进程逐项校验参数个数、顺序、管道前缀与父进程 PID）。stdin/stdout/stderr 均为管道。
3. worker 校验父进程：父进程 PID 与 `--parent-pid` 一致、父进程映像为 `<安装目录>\sing-box.exe` 且与磁盘文件为同一文件、父进程命令行不含 `--type` 参数、父进程的父进程不是 `sing-box.exe`、父进程签名证书与 worker 相同、父进程创建早于 worker。任一不满足即退出（stderr 给出原因）。
4. worker 创建 P1、P2（DACL：SYSTEM、Administrators 与 GUI 用户），只接受进程 PID 等于 GUI PID 的客户端；就绪后 stdout 输出 `READY` 换行。GUI 在 10 秒内未读到 `READY`，或首行不是 `READY`，即终止子进程并报错（14.3 E-DAEMON-02）。stderr 持续保留末尾 64 KiB，用于 worker 退出时的错误详情。
5. GUI 以 gRPC（HTTP/2 明文）连接：P1 的 authority 为 `sing-box-worker`，挂载 ApplicationService；P2 的 authority 为 `sing-box`，挂载 DesktopService、StartedService、ManagedService。worker 对 P2 上的每个连接拨号守护进程管道，校验管道服务端为正在运行的 `sing-box-daemon` 服务进程（会话 0、LocalSystem、映像与 worker 为同一文件、签名证书相同）后双向转发。
6. 所有调用附带元数据 `accept-language: <界面语言 BCP47>`，守护进程与 worker 据此返回本地化错误。
7. GUI 退出时关闭 worker 的 stdin，worker 读到 EOF 后退出；worker 亦监视父进程句柄，父进程退出即关闭全部连接并退出。worker 意外退出时，GUI 在下次调用时重新拉起（单飞，避免并发重复启动），调用错误替换为 worker 的退出信息（退出码与 stderr 末尾）。

### 2.3.2 GUI 进程形态约束（由守护进程的进程角色校验决定）
- GUI 可执行文件名必须为 `sing-box.exe`，位于安装根目录；守护进程以 `resources\daemon\sing-box-daemon.exe` 的上两级目录推算该路径，不可配置。
- 发起 worker 与连接 P1/P2 的必须是同一个 GUI 主进程；不得通过辅助进程、外壳进程或 `cmd`/PowerShell 间接启动 worker。
- GUI 主进程不得由另一个 `sing-box.exe` 进程作为父进程启动并继续运行。应用内“重新启动”（语言切换、更新后重启等）必须先让旧进程退出再启动新进程（例如由新进程等待旧进程句柄结束后再启动 worker），或经资源管理器以用户身份启动。
- GUI 主进程命令行不得包含 `--type` 参数（该参数为 Electron 子进程标记，守护进程会拒绝）。
- GUI 必须运行在交互会话（会话 ID ≠ 0），以普通用户身份运行即可，不需要也不应以管理员身份运行。
- MyGo 运行时若存在额外的启动器进程或进程内托管方式，必须在 M0 验证其不改变上述父子关系与映像路径（19 章 M0）。

### 2.3.3 架构选择理由
- **为何使用官方守护进程**：官方守护进程已实现服务、TUN、系统代理、所有权、报告、更新安装与完整的本地进程认证，并随核心版本同步发布于同一源码树。原样构建即可获得与官方桌面客户端一致的行为与安全边界，无需自行移植后端平台代码；上游升级仍须检查全部通信协议、行为和安装约束，适配前端并通过真实升级验证。
- **为何以自签名证书满足签名要求**：守护进程以 WinVerifyTrust 验证签名，对“根证书不受信任”与“证书链不完整”两类结果，转而检查签名证书是否为有效期内、具备代码签名用途的自签名证书；守护进程只比较 GUI、worker 与自身的签名证书是否逐字节相同，不要求证书受系统信任。因此项目自有的自签名证书即可满足要求，用户机器无需安装或信任任何证书（第 21 章）。该结论来自源码分析，必须在 M0 于真实 Windows 上验证（20.5 SIG-01～SIG-08）；验证失败时按 A-29 报告阻塞，不得自行修改后端或启用附录 C。
- **为何使用服务而非提权 GUI**：与基线一致，macOS 上核心运行于系统扩展，退出应用后连接继续；服务模式下 GUI 退出、注销重登都不影响核心；开机启动与按需启动无需每次 UAC 提示；GUI 以普通权限运行，资源管理器拖放、文件对话框、通知均按普通应用工作。官方守护进程只以服务形态接受连接（worker 会校验管道服务端是正在运行的服务进程），因此本应用不提供无服务的提权运行方式。

## 2.4 接口清单

GUI 只通过下列 gRPC 服务与守护进程和 worker 交互；桩代码由 16.1 规定的完整协议集合生成到 `internal/rpc/gen`，包含桌面服务协议及递归导入依赖。GUI 模块不导入 sing-box Go 模块（避免 Go 版本与依赖冲突）。

| proto 文件（核心源码树） | 服务 | 连接 | 主要用途 |
|---|---|---|---|
| `daemon/started_service.proto` | StartedService | P2（经 worker 中继） | `SubscribeServiceStatus`、`SubscribeStatus`（内存、goroutine、连接数、上下行速率与累计、traffic_available）、`SubscribeLog`/`GetDefaultLogLevel`/`ClearLogs`、`SubscribeGroups`/`SelectOutbound`/`URLTest`/`SetGroupExpand`、`GetClashModeStatus`/`SubscribeClashMode`/`SetClashMode`、`SubscribeConnections`/`CloseConnection`/`CloseAllConnections`、`GetDeprecatedWarnings`、`GetStartedAt`、`SubscribeOutbounds`、网络质量与 STUN 测试、Tailscale/Taildrop/USB/OpenConnect/OpenVPN 相关 RPC、`SubscribeNotifications` |
| `daemon/managed_service.proto` | ManagedService | P2 | `StopService`、`ReloadService`、`GetSystemProxyStatus`/`SetSystemProxyEnabled`、`TriggerDebugCrash`、`TriggerOOMReport` |
| `experimental/boxdd/desktop_service.proto` | DesktopService | P2 | `GetDaemonInfo`（版本、所有权 AVAILABLE/CALLER/OTHER）、`ClaimService`、`TakeOverService`、`StartService`（配置内容 + StartOptions：oom_killer_enabled / oom_killer_disabled / oom_memory_limit / power_report_enabled）、`GetWorkingDirectory`/`DestroyWorkingDirectory`、崩溃/OOM/功耗报告的列表/读取/标记已读/导出/删除/全部删除、`InstallUpdate`、`GetSecuritySettings`/`SetInsecureModeEnabled`、`SetLocale` |
| 同上 | ApplicationService | P1（worker 本地） | `CheckConfig`、`FormatConfig`、`GenerateConfigSchema`、`EncodeProfile`/`DecodeProfile`（.bpf）、`ArchiveReport`、`StartStandaloneNetworkQualityTest`、`StartStandaloneSTUNTest` |

- 本地命令行接口（GUI 以普通权限调用，不经 gRPC）：`sing-box-daemon.exe version`（输出行 `sing-box-daemon version <版本>`，用于读取随附守护进程版本）与 `sing-box-daemon.exe service status`（退出码 0 运行中、2 未运行、3 未安装，其他视为未知）。
- 需要管理员权限的命令（经 UAC 执行，15.2）：`service install --working-directory <守护进程数据目录>`、`service start`、`service uninstall`、`service set-insecure-mode true`。
- 远程控制（第 11 章）使用同一 StartedService/ManagedService 桩，经 HTTP/2（TLS 或明文，依 URL scheme）连接远端 `api` 服务，元数据 `authorization: Bearer <secret>`；不经过 worker。

### 2.4.1 服务所有权
- 启动前调用 `GetDaemonInfo`：
  - `AVAILABLE`：调用 `ClaimService` 后 `StartService`。
  - `CALLER`：本用户已拥有，直接操作。
  - `OTHER`：另一个 Windows 用户拥有服务。弹出提示“服务正被其他用户使用”，提供“接管”按钮调用 `TakeOverService`（文案见第 14 章）。
- 所有者决定系统代理写入哪个用户的注册表、`process_*` 规则的用户上下文与守护进程按用户划分的工作目录。所有者注销时核心继续运行；所有者会话的系统代理随注销失效，重新登录后恢复（守护进程既有行为）。
- 守护进程版本（`GetDaemonInfo.version`）与随附守护进程版本（`version` 子命令）不一致时（安装中断、服务指向旧文件等），仪表盘显示“服务需要修复”，按钮执行 15.2 修复。

## 2.5 启动服务流程（Start）

1. 读取选中配置文件内容（`configs\config_<id>.json`）。
2. 应用配置重载（第 11.6 节）与隧道选项映射（第 11.4 节），得到最终 JSON。
3. 调用 ApplicationService.`CheckConfig`，失败则弹出错误并中止。
4. 按 2.4.1 处理所有权。
5. 调用 DesktopService.`StartService`，`StartOptions` 取自偏好：`oom_killer_enabled`、`oom_memory_limit`（MB→字节）、`power_report_enabled`。
6. 订阅 `SubscribeServiceStatus`，状态依次为 `STARTING` → `STARTED`（或 `FATAL` 含 `errorMessage`）；仪表盘与托盘随之更新。
7. 记录偏好 `started_by_user = true`（供开机启动后自动连接与按需启动判断）。

停止：ManagedService.`StopService`，并置 `started_by_user = false`。重载：ManagedService.`ReloadService`（配置变更、重载项变更时）。隧道选项变更时执行“停止后重新启动”（与基线 Packet Tunnel 页一致）。

## 2.6 安装布局（与 sing-box-for-desktop 一致）

```
<安装目录>（默认 C:\Program Files\sing-box\）
├─ sing-box.exe                          GUI（MyGo 构建产物，自签名证书签名）
├─ resources\
│  └─ daemon\
│     ├─ sing-box-daemon.exe             官方守护进程（服务 / worker；自签名证书签名）
│     ├─ libcronet.dll                   按 amd64/arm64 从锁定的对应模块暂存（naive 出站）
│     ├─ WinDivert64.sys / WinDivert32.sys  按架构暂存，驱动由其发布者签名
│     └─ VBoxUSB.* / VBoxUSBMon.sys / usbip2_ude.* / usbip2_filter.*  按架构暂存（10.6.3），驱动由其发布者签名
├─ Uninstall sing-box.exe
└─ （MyGo 运行时附带的库，如 sqlite、libghostty-vt）
```

- 路径约束（守护进程硬性要求）：守护进程可执行文件名必须为 `sing-box-daemon.exe`，其所在目录名必须为 `daemon`，上一级目录名必须为 `resources`；GUI 必须为上述 `resources` 的上一级目录中的 `sing-box.exe`。名称比较不区分大小写。
- `resources\daemon\` 中的文件即官方构建脚本的输出目录内容，原样复制，不改名、不重新打包驱动；本项目只对 `sing-box-daemon.exe` 追加 Authenticode 签名（签名不修改程序代码，见 21.2）。
- 数据目录：
  - 应用数据目录：默认 `%APPDATA%\sing-box`（每用户）；自定义安装可改为固定共享目录（15.2.2）。
  - 守护进程数据目录：默认 `C:\ProgramData\sing-box-daemon`（守护进程工作目录，第 13 章）。
  - 两者记录在注册表 `HKLM\SOFTWARE\SagerNet\sing-box`（64 位视图）：`LayoutVersion`（DWORD，固定 2）、`ApplicationDataDirectory`（字符串，空值表示每用户默认目录）、`DaemonDataDirectory`（字符串）。GUI 启动时读取该键；`LayoutVersion` 存在但不为 2 时拒绝启动并提示重新安装。键名与官方客户端相同（共存影响见 15.10）。
- 安装、修复、卸载与安装路径安全检查见 15.2。

## 2.7 线程与状态模型

- UI 构建在 MyGo 主线程；所有 gRPC 调用在 goroutine 中执行，结果通过 MyGo 的主线程调度回写状态并请求重绘。
- 全局状态对象 `AppState`（对应基线 `ExtensionEnvironments`）：当前服务状态、选中配置、配置列表、命令客户端（订阅：status、groups、logs、clash mode、connections）、远程服务器、日志/连接搜索文本缓存、工具页徽标计数、导入请求。
- 订阅生命周期：主窗口可见或托盘菜单打开时订阅 status/groups/clash mode；日志订阅在服务运行期间常驻（缓冲 3000 行，见第 9 章）；连接订阅仅在连接页可见时存在。窗口隐藏后 3 秒取消非必要订阅以节省资源（与基线 `controlActiveState` 行为一致）。

## 2.8 状态枚举

服务状态（与基线一致）：`invalid`、`disconnected`、`connecting`、`connected`、`reasserting`、`disconnecting`。
- `isConnected` = connecting/connected/reasserting；`isConnectedStrict` = connected；`isSwitchable` = connected/disconnected；`isEnabled`（按钮可用）= 非 connecting/disconnecting。
- 映射（`ServiceStatus.Type`）：`IDLE` → disconnected；`STARTING` → connecting；`STARTED` → connected；`STOPPING` → disconnecting；`FATAL` → disconnected，并以 `errorMessage` 弹出“启动失败”警告；`ReloadService` 进行中 → reasserting；守护进程服务未安装、未运行或 worker 无法建立 → invalid。
- 状态订阅 `SubscribeStatus` 的 `interval` 取 `1e9`（单位为纳秒，即 1 秒），与基线刷新频率一致。

## 2.9 安全模型（守护进程既有机制）

守护进程以 LocalSystem 运行核心，且核心配置可指定文件路径（日志输出、缓存文件、规则集等），因此能驱动守护进程的进程等同于取得高权限。官方守护进程以“已安装位置 + 同一文件 + 同一签名证书”认证本地客户端，本项目原样沿用，不增加、不削弱任何检查。

### 2.9.1 守护进程启动时
1. 打开并锁定自身可执行文件，解析最终路径，按 2.6 路径约束推算安装目录与 `sing-box.exe` 路径；不符合布局即启动失败。
2. 读取自身 Authenticode 签名证书（2.9.4），作为本次运行的“守护进程签名者”。无签名或签名验证失败即启动失败。
3. 服务安装时（`service install`）还会：校验 GUI 与守护进程签名证书相同；校验安装目录位于本地固定 NTFS 卷；安装目录各级上级目录不是重解析点，且所有者与可写/可删除/可改权限的主体只限 SYSTEM、Administrators、TrustedInstaller；安装目录树内无重解析点；随后把安装目录树 ACL 重置为受保护的 `O:SY G:SY D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;GRGX;;;AU)`（文件为同权限不继承版本）。守护进程数据目录同样校验卷与上级目录，并设置为仅 SYSTEM、Administrators 与服务 SID 完全控制的受保护目录。
4. `--allow-unsafe-installation-directory-permissions` 只跳过路径与权限检查及加固，**不跳过签名比较**；本项目的安装器默认不使用该参数，仅在用户于“不安全路径”页明确确认后传入（15.2.2）。

### 2.9.2 每个连接的认证（守护进程管道）
管道 `\\.\pipe\ProtectedPrefix\Administrators\sing-box` 只有管理员/SYSTEM 可创建，DACL 为 SYSTEM、Administrators 完全控制，Authenticated Users 读写。每个连接：
1. 取客户端 PID，客户端必须是交互会话（会话 ≠ 0）中的进程。
2. 客户端映像最终路径必须等于守护进程自身路径，且为同一文件（卷序列号 + 文件索引），即客户端必须是本安装的 worker；客户端签名证书必须与守护进程签名者逐字节相同。
3. 客户端命令行必须符合 2.3.1 第 2 步的 worker 形态，`--parent-pid` 等于真实父进程 PID。
4. 父进程与 worker 的用户 SID、会话 ID 相同；父进程创建时间早于 worker。
5. 父进程映像最终路径等于 `<安装目录>\sing-box.exe` 且为同一文件；父进程符合 2.3.2 的进程形态；父进程签名证书与守护进程签名者逐字节相同。
6. 校验期间 worker 与父进程均未退出。通过后，该连接以父进程（GUI）的用户 SID、会话 ID、PID 作为调用者身份，用于所有权（2.4.1）与模拟用户令牌（系统代理、进程规则）。

### 2.9.3 worker 侧校验
- 启动时校验父进程（2.3.1 第 3 步）。
- P1/P2 只接受 PID 等于 GUI PID 的客户端。
- 中继到守护进程前校验管道服务端：会话 0、是正在运行的 `sing-box-daemon` 服务的进程、服务以 LocalSystem 运行、映像与 worker 为同一文件、签名证书相同。

### 2.9.4 签名证书的取得与判定（决定自签名方案可行性）
守护进程对每个被检查的可执行文件执行：
1. `WinVerifyTrust`（通用验证策略 V2，无界面，不检查吊销，仅使用缓存的 URL 检索，禁用 MD2/MD4）。结果为成功、`CERT_E_UNTRUSTEDROOT` 或 `CERT_E_CHAINING` 时继续；其他结果（包括 `TRUST_E_NOSIGNATURE` 无签名、`TRUST_E_BAD_DIGEST` 文件被改动、`CERT_E_EXPIRED` 等）一律拒绝。
2. 取签名者证书链第 0 个证书（叶证书）的 DER 编码。
3. 证书的扩展密钥用法必须包含“代码签名”（1.3.6.1.5.5.7.3.3）或“任意用途”。
4. 当第 1 步结果为“根不受信任”或“链不完整”时，额外要求：证书主题与颁发者的原始编码相同；证书自身签名可用自身公钥验证通过；**当前时间**位于证书有效期 [NotBefore, NotAfter] 内。
5. 返回的 DER 编码用于逐字节比较：GUI、worker、守护进程（以及 `InstallUpdate` 的安装程序）必须由**同一张证书**签名；同一密钥重新签发的证书也视为不同签名者。

由此得出的证书要求、到期影响与轮换方式见 21.1。

### 2.9.5 信任边界说明
- 能够在 `<安装目录>` 中替换文件的主体只有管理员与 SYSTEM（安装目录受保护 ACL），因此“同一路径 + 同一文件 + 同一签名证书”保证了驱动守护进程的只能是本安装的 GUI。
- 自签名证书不提供发布者身份证明，只提供“GUI 与守护进程来自同一构建方”的绑定；对外的发布完整性由 SHA256SUMS 与 Ed25519 发布签名保证（21.3）。
- 私钥泄露的影响：攻击者可签署能通过守护进程比较的程序，但仍须先以管理员身份把它放入受保护的安装目录，因此不构成本地提权；处置方式为轮换证书（21.1.4）。
