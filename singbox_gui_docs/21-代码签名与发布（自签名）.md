# 21 代码签名与发布（自签名）

## 21.1 自签名代码签名证书

本应用使用项目自有的**自签名**代码签名证书。同一张证书签署三类文件：GUI `sing-box.exe`、守护进程 `sing-box-daemon.exe`、安装包 `sing-box-<版本>-windows-<arch>-setup.exe`（以及卸载程序）。签名的唯一目的是满足官方守护进程的“同签名者”要求（2.9）；它不提供发布者身份，也不消除 SmartScreen 警告（21.4）。

### 21.1.1 守护进程如何判定签名者
守护进程对 GUI、worker、自身和更新安装包使用同一判定（2.9.4）：
1. 以 `WinVerifyTrust`（通用验证策略 V2，无界面，不检查吊销，只用本地缓存的 URL，禁用 MD2/MD4）验证文件的 Authenticode 签名。结果只能是“成功”“根证书不受信任（CERT_E_UNTRUSTEDROOT）”或“证书链错误（CERT_E_CHAINING）”三者之一，其他结果一律拒绝，例如无签名、文件被篡改（摘要不符）、证书过期（受信任链上）。
2. 取签名者证书（证书链第 0 个，即叶证书）的 DER 编码。
3. 叶证书的扩展密钥用法必须包含“代码签名”（1.3.6.1.5.5.7.3.3）或“任意用途”。没有扩展密钥用法扩展也会被拒绝。
4. 若第 1 步结果是“根不受信任”或“链错误”（自签名证书在未安装到受信任根的机器上就是这种情况），叶证书还必须同时满足：
   - 主题与颁发者的原始编码逐字节相同（自签名）；
   - 用证书自身公钥验证自身签名成功（Go 标准库规则：不接受 SHA-1、MD5 签名；RSA 密钥不得小于 1024 位）；
   - **当前时间**在 NotBefore 与 NotAfter 之间（含边界）。
5. 两个文件的签名者 DER **逐字节相同**才算同一签名者。用同一私钥重新签发的证书（序列号、有效期不同）也视为不同签名者。

守护进程**不**检查：时间戳、证书最长有效期、KeyUsage、BasicConstraints、证书主题内容、证书是否安装在任何存储中。

### 21.1.2 证书规格（必须满足）
| 项目 | 取值 | 说明 |
|---|---|---|
| 类型 | X.509 v3，自签名（主题 = 颁发者） | 21.1.1 第 4 步 |
| 密钥 | RSA 3072 位（备选：ECDSA P-256） | Authenticode 不支持 Ed25519；RSA 兼容性最好 |
| 签名算法 | sha256WithRSAEncryption（ECDSA 时 ecdsa-with-SHA256） | 不得用 SHA-1 |
| 扩展密钥用法 | 仅 codeSigning（1.3.6.1.5.5.7.3.3） | 必须存在 |
| 密钥用法 | digitalSignature | 守护进程不查；按代码签名证书惯例设置 |
| 基本约束 | 不含该扩展或 CA:FALSE | 守护进程不查；不得为 CA:TRUE，避免被误用为 CA |
| 主题 | `CN=<产品名> Code Signing, O=<项目名>`（A-10） | 显示在文件属性“数字签名”页，不显示在 UAC 中 |
| 有效期 | NotBefore = 生成时间 − 1 天；NotAfter = NotBefore + 10 年（A-32） | 回拨 1 天避免时钟偏差导致“尚未生效” |
| 序列号 | 128 位随机 | — |
| 签名摘要 | 文件摘要 SHA-256（`/fd SHA256`） | — |
| 时间戳 | 不加（A-33） | 对守护进程判定无影响 |

### 21.1.3 过期与时间相关行为
- 证书一旦过期，守护进程验证自身可执行文件失败，服务**无法启动**；正在运行的服务在下一次连接时也会拒绝 GUI 与 worker。结果是该版本完全无法连接（E-DAEMON-06）。
- 用户系统时间早于 NotBefore 时同样失败；GUI 自检区分两种情况给出提示（14.3）。
- 恢复：更新检查、下载、Ed25519 校验与 UAC 安装都不依赖守护进程（12.5.1），用户点击“检查更新”即可安装由有效证书签名的新版本。
- 因此证书必须在过期前很久完成轮换，并保证用户有足够时间更新：
  - `cert-expiry.yml`（22.5）每周检查 `keys/codesign.cer`，剩余不足 18 个月时开议题；
  - 轮换最晚在剩余 12 个月时完成（21.1.4）。

### 21.1.4 轮换
触发：计划轮换（剩余有效期不足 12 个月）、私钥疑似泄露、规格变更。

1. 维护者在离线环境运行 `scripts/sign/New-SelfSignedCert.ps1` 生成新证书（21.1.5），把新 PFX（Base64）与密码写入 GitHub 环境机密 `CODESIGN_PFX_BASE64`、`CODESIGN_PFX_PASSWORD`，替换 `keys/codesign.cer`，在同一 PR 中更新 `keys/codesign.cer.sha256`。
2. 下一个发布由新证书签名 GUI、守护进程与安装包（三者始终同一证书）。
3. 已安装旧版本的用户更新时：旧守护进程比较安装包签名者与自身不同，`InstallUpdate` 返回 `SIGNER_MISMATCH`，更新器自动改走 UAC 路径（12.5），用户多确认一次 UAC。安装完成后新 GUI 与新守护进程签名者一致，恢复正常。
4. 发布说明注明“本版本更换了签名证书，更新时会出现一次管理员确认”。
5. 私钥泄露时另外：立即删除旧机密；尽快发布新证书版本；在发布页公告旧证书指纹作废。旧证书签名的程序仍会被旧版本守护进程接受，但攻击者要利用它必须先有管理员权限把文件放进受保护的安装目录（2.9.5），因此风险限于已获管理员权限的攻击者。

### 21.1.5 证书生成脚本
`scripts/sign/New-SelfSignedCert.ps1`（Windows PowerShell 5.1 / PowerShell 7）：
```powershell
param(
  [string]$Subject = "CN=sing-box GUI Code Signing, O=<项目名>",   # A-10
  [int]$Years = 10,
  [string]$Out = "build\cert"
)
$notBefore = (Get-Date).ToUniversalTime().AddDays(-1)
$cert = New-SelfSignedCertificate -Type CodeSigningCert -Subject $Subject `
  -KeyAlgorithm RSA -KeyLength 3072 -HashAlgorithm SHA256 `
  -KeyExportPolicy Exportable -KeyUsage DigitalSignature `
  -NotBefore $notBefore -NotAfter $notBefore.AddYears($Years) `
  -CertStoreLocation Cert:\CurrentUser\My
$password = Read-Host -AsSecureString "PFX password"
New-Item -ItemType Directory -Force $Out | Out-Null
Export-PfxCertificate -Cert $cert -FilePath "$Out\codesign.pfx" -Password $password | Out-Null
Export-Certificate -Cert $cert -FilePath "$Out\codesign.cer" -Type CERT | Out-Null
Remove-Item "Cert:\CurrentUser\My\$($cert.Thumbprint)"   # 不在证书存储中保留
go run ./scripts/sign/check-cert.go "$Out\codesign.cer"  # 校验 21.1.2 全部规格
```
- `-Type CodeSigningCert` 生成扩展密钥用法为 codeSigning 的自签名证书。
- 非 Windows 环境可用等价的 OpenSSL 命令（README 给出）：`openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 -nodes -subj "/CN=…" -addext "extendedKeyUsage=codeSigning" -addext "keyUsage=critical,digitalSignature" -addext "basicConstraints=critical,CA:FALSE"`，再用 `openssl pkcs12 -export` 生成 PFX；签名使用 `osslsigncode`。
- `check-cert.go` 检查：自签名且自身签名可验证、SHA-256 签名、RSA ≥ 3072 或 ECDSA P-256、EKU 含 codeSigning、剩余有效期 ≥ 18 个月（生成时应为约 10 年）。CI 每次发布都运行一次。

### 21.1.6 用户机器无需安装证书
- 守护进程接受“根不受信任”的自签名证书（21.1.1），因此用户机器**不需要**、安装器也**不会**把证书导入任何证书存储。
- 文档与 README 明确提示用户**不要**把本项目证书导入“受信任的根证书颁发机构”：这样做会让该证书签名的任何程序在本机被视为可信发布者，扩大私钥泄露的影响，且对本应用的运行没有任何帮助。
- 即使用户导入了证书，守护进程的判定结果不变（仍比较 DER），只是第 4 步不再执行。

## 21.2 签名流程
`scripts/sign/sign.ps1` 在 GitHub Actions 的 `windows-latest` 上运行（22.4），只在 `release` 环境中拿到私钥：

1. 从 `CODESIGN_PFX_BASE64` 解码 PFX 到 `$env:RUNNER_TEMP\codesign.pfx`（作业结束时删除）。
2. 校验 PFX 中证书的 SHA-256 指纹与仓库 `keys/codesign.cer.sha256` 一致，防止误用其他证书。
3. 用 Windows SDK `signtool` 签名：`signtool sign /fd SHA256 /f codesign.pfx /p <密码> <文件>`。顺序：
   1. `sing-box.exe`、`resources\daemon\sing-box-daemon.exe`（在 NSIS 打包之前）；
   2. NSIS 生成的卸载程序（NSIS 构建期间回调签名，`!uninstfinalize`）；
   3. 安装包 `sing-box-<版本>-windows-<arch>-setup.exe`（`!finalize`）。
   - 驱动文件（`.sys`、`.cat`）与 `libcronet.dll` 保持上游原样，不重新签名。
4. 校验：对上述每个文件运行 `go run ./scripts/sign/verify.go`，它以与守护进程相同的规则（21.1.1）提取签名者，要求三者 DER 与 `keys/codesign.cer` 逐字节相同；任一不同则中止发布。
5. 删除 PFX 文件；签名步骤不输出密码与证书内容。

## 21.3 发布完整性：SHA256SUMS 与 Ed25519 签名
- 自签名证书无法向用户证明“文件来自本项目”（任何人都能生成同名主题的自签名证书），因此发布文件的来源与完整性仍由以下两层保证：
  1. `SHA256SUMS`：列出该发布全部资产的 SHA-256，GNU coreutils 格式，每行 `<64 位小写十六进制>  <文件名>`，按文件名排序；
  2. `SHA256SUMS.sig`：项目更新私钥对 `SHA256SUMS` 文件内容的 SHA-256 摘要的 Ed25519 签名（Base64），与 MyGo 更新清单的签名方案相同。签名后立即用编译进 GUI 的公钥自检，失败则中止发布。
- 应用内更新先验证这两层（12.5），再交给守护进程或 UAC 安装。
- 分发渠道只有本项目 GitHub Releases（地址见 A-10）。不在第三方下载站发布。
- 代码签名证书的 SHA-256 指纹同时写在 README 与每个发布说明中，供用户在文件属性“数字签名 → 详细信息 → 查看证书”中核对。

### 21.3.2 公钥与手动验证
- 公钥同时发布在三处：
  - 仓库 `keys/release-ed25519.pub`（Base64）与 `keys/release-ed25519.pub.pem`（PEM）；
  - README；
  - 每个发布的说明中。
- GUI 在构建时以 `-ldflags "-X <module>/internal/update.releasePublicKeys=<Base64>[,<Base64>]"` 注入公钥，可注入多个，供密钥轮换使用。
- 手动验证（README 给出，Windows 自带工具即可完成第一步）：
  1. `certutil -hashfile sing-box-<版本>-windows-amd64-setup.exe SHA256`，结果与 `SHA256SUMS` 中对应行比对。
  2. 验证 `SHA256SUMS` 本身（需 OpenSSL 3）：
     ```
     openssl dgst -sha256 -binary SHA256SUMS > sums.digest
     openssl base64 -d -A -in SHA256SUMS.sig -out sums.sig
     openssl pkeyutl -verify -pubin -inkey release-ed25519.pub.pem -rawin -in sums.digest -sigfile sums.sig
     ```
     输出 `Signature Verified Successfully` 即通过。
  3. 也可以运行 `sing-box.exe --verify-release --sums SHA256SUMS --sig SHA256SUMS.sig [--file <资产>]`（无界面模式，使用内置公钥），退出码 0 表示通过。

### 21.3.3 密钥管理
- 生成：维护者在离线环境用 `mygo keygen` 生成 Ed25519 密钥对（Base64），再转换出 PEM 公钥。
- 存放：私钥只存在于以下位置，不进入仓库、不出现在构建日志：
  - GitHub Actions 环境机密 `RELEASE_ED25519_PRIVATE_KEY`，只属于 `release` 环境（22.6）；
  - 两份离线备份（加密）。
- 权限：仓库开启分支保护与必需评审；`release` 环境只允许 `main` 分支与 `v*` 标签上运行的工作流使用（22.6）；所有维护者开启 MFA。
- 轮换（A-28）：
  1. 新版本 GUI 同时内置旧、新两个公钥；
  2. 之后的发布改用新私钥签名；
  3. 旧公钥在两个大版本后移除。
- 私钥疑似泄露时：
  1. 立即移除机密；
  2. 发布只内置新公钥的版本，该版本用新私钥签名；
  3. 在发布页公告，旧版本用户需手动下载该版本。
- 私钥与 MyGo 更新签名使用同一格式，但本应用不启用 MyGo 自带的更新清单（12.5）。

## 21.4 用户会看到什么

本节内容同时用于 README、发布说明和常见问题，开发者无需在应用内实现额外界面。

### 21.4.1 SmartScreen：“Windows 已保护你的电脑”
- 触发：运行从浏览器下载的安装包时出现。文件带有网络标记（Mark-of-the-Web），而自签名证书不链到受信任根，Windows 视同无发布者信誉。
- 表现：蓝色对话框“Windows 已保护你的电脑 / Microsoft Defender SmartScreen 阻止了无法识别的应用启动。”；点击“更多信息”后显示“发布者：未知发布者”，并出现“仍要运行”。
- 用户操作：更多信息 → 仍要运行。新版本通常会再次出现警告（自签名证书不积累发布者信誉）。
- 应用内更新下载的安装包不带网络标记，通常不触发 SmartScreen。

### 21.4.2 浏览器下载警告
- Edge 或 Chrome 可能提示“不常下载”或“可能有害”，并默认隐藏或删除下载。
- 用户操作：Edge：下载面板 → “…” → 保留 → 显示更多 → 仍然保留；Chrome：下载面板 → “仍然保留”。
- 本项目只在 GitHub Releases 发布，请用户核对网址与 SHA-256（21.3.2）。

### 21.4.3 杀毒软件误报
代理客户端会创建虚拟网卡、修改系统代理、以 SYSTEM 运行服务，自签名程序也没有信誉，可能被启发式规则误报。

**项目侧缓解措施（发布前必须执行）：**
1. 不使用 UPX 等加壳或压缩，不做代码混淆，不在运行时下载并执行代码。
2. GUI 嵌入完整的版本资源与清单（18.4）。文件名各版本保持不变：`sing-box.exe`、`sing-box-daemon.exe`、卸载程序。
3. 构建可复现（`-trimpath`、固定工具链），签名前的可执行文件哈希可由任何人从源码复现（21.5）。
4. 发布前用 Microsoft Defender 命令行（`MpCmdRun -Scan -ScanType 3`）扫描全部产物，有检出则中止并转人工处理（22.4）。发布后用 VirusTotal 查询哈希，把结果链接写入发布说明。
5. 出现误报时，在发布页置顶说明，并向相关厂商提交误报申诉，附发布页链接与 SHA-256：Microsoft 使用 Security Intelligence 提交入口（“软件开发者”“误报”）；其他厂商使用各自入口。每个发布在检查清单中记录申诉状态。
6. 不向用户建议全局关闭杀毒软件。只建议在核实哈希后，把安装目录加入排除项。

**用户侧可能现象：** 安装失败，或安装后 `sing-box-daemon.exe` 被隔离：仪表盘显示“服务未安装”，或修复失败。E-DAEMON-01、E-DAEMON-02、E-DAEMON-07 的错误详情附加核实哈希后恢复文件的提示（14.3）。

### 21.4.4 UAC 显示“未知发布者”
自签名证书不链到受信任根，UAC 对话框为黄色横条样式，发布者显示“未知”，属正常现象。出现 UAC 的操作：
- 运行安装包、卸载；
- 安装 / 启动 / 修复服务（显示程序名 `sing-box-daemon.exe`）；
- 开启非网络特权模式（11.3）；
- 应用更新走 UAC 路径时（证书轮换后、GUI 修订版、守护进程不可用时）。守护进程 `InstallUpdate` 路径不出现 UAC。

### 21.4.5 其他系统策略
- Windows 11“智能应用控制”处于强制模式时，可能直接阻止无信誉的程序，并且没有“仍要运行”选项。此时只能在“Windows 安全中心 → 应用和浏览器控制”中调整智能应用控制，或等待将来提供商业证书签名版本（21.6）。README 如实说明这一点。
- 企业设备的应用控制策略（WDAC/AppLocker）可能禁止本程序；管理员可按本项目证书（发布者规则）放行。

## 21.5 从源码构建
- 官方守护进程要求 GUI 与守护进程同签名者，因此从源码构建**必须签名**，但构建者用自己的证书即可，无需本项目私钥：
  1. `scripts/sign/New-SelfSignedCert.ps1 -Out build\cert`（21.1.5）生成自己的证书；
  2. `scripts/build-all.ps1 -Arch amd64 -Pfx build\cert\codesign.pfx`：依次构建守护进程（build_boxdd）、GUI、签名、NSIS 打包、签名安装包、校验签名者一致；不生成 Ed25519 签名、不发布。
- 构建结果与发布版功能完全相同：构建脚本、构建标签、驱动暂存规则一致；不存在仅发布版才有的代码路径。
- 源码构建与官方发布签名者不同，二者不能混装或互相原地升级（15.10）；更换来源需先卸载。
- 更新公钥：未注入公钥时“检查更新”照常工作，“更新”按钮改为打开发布页（12.5）；自行分发者可生成自己的 Ed25519 密钥对并注入自己的公钥与发布仓库。
- 复现验证：Authenticode 签名嵌在 PE 文件中，签名后的哈希必然不同。复现方法：`go run ./scripts/sign/strip.go <文件>` 去除签名证书表后再计算 SHA-256，与发布页 `SHA256SUMS.unsigned`（同在 `SHA256SUMS` 签名范围内）对比。NSIS 安装包含时间戳，不要求一致。

## 21.6 未来可选：商业代码签名
自签名满足运行需要；商业证书只用于改善 SmartScreen、UAC 与杀毒软件体验（A-25）：
- **SignPath Foundation**：为符合条件的开源项目免费提供签名；证书颁发给 SignPath Foundation，密钥保存在其 HSM 中，通过 GitHub Actions 集成。申请条件：OSI 许可证、公开仓库、自动化构建、已有发布、维护者开启 MFA、遵守其行为准则（需注意“不得包含规避安全措施的功能”条款，申请时说明用途）。
- **Azure Artifact Signing**（原 Trusted Signing）：按月付费的托管签名服务，与 CI 集成；个人开发者目前仅限美国与加拿大，组织可在包括日本在内的多个地区申请。
- 切换到商业证书时，GUI、守护进程、安装包必须同时切换（同签名者要求）。注意守护进程比较的是叶证书 DER：托管签名服务若频繁轮换短期叶证书（例如每几天一张），每张新叶证书都会被视为不同签名者，导致各版本之间 `InstallUpdate` 都返回 `SIGNER_MISMATCH`，更新始终走 UAC。选择服务前需确认其叶证书的轮换周期。
- 切换后行为与 21.1.4 的轮换相同：首次更新走 UAC。
